## DSH 使用约定

本技能提供指令和本地资料，不注册新工具。仅调用当前会话实际提供的工具；若工具通过 `run_code` 暴露，在其中调用 `tools.<工具名>`，不要直接调用未声明的工具。

技能内的参考资料路径相对宿主提供的技能资源根目录（`Base directory for this skill`）解析；用户文件、调研结果和代码输出路径相对当前工作区或用户确认的输出目录解析，不写入技能资源目录。只按需读取资料。

读取文本使用 `read({file_path, offset, limit})`，搜索内容使用 `grep({pattern, path})`，发现文件使用 `glob({pattern, path})`；`glob` 不列目录，目录存在性或目录列表使用 `bash`。修改现有文件前先 `read`，精确修改使用 `edit({file_path, old_string, new_string})`，创建文件使用 `write({file_path, content})`。不得覆盖未经确认的已有输出；写入后重新读取验证。

# 直播知识提炼（live-knowledge-distiller）

> **本 Skill 是「指引型」，不暴露 MCP 工具，不提供完整代码模板。**
> 它教 AI 在拿到直播转录文本后，应该如何评估、提取、结构化沉淀知识。
> 具体输出文档由 AI 根据场景自主生成。

## 何时激活此 Skill

满足以下任一条件时激活：

- 用户给了一段直播/视频的文稿，要求「总结」「提炼」「提取知识点」
- 用户提到「直播转录」「文稿文本」「视频文字稿」并要求分析
- 工作流中已有 .txt 转录文件，需要转为结构化知识文档（MD）
- 任何需要将非结构化语音转录转化为可检索知识笔记的场景

不要激活的场景：

- 用户只想下载视频（此能力不在本技能范围内；仅在可用时选择下载工具或 `bili-archiver`，不假定已安装）
- 用户只想做语音转文字（此能力不在本技能范围内；仅在可用时选择转录工具或 `local-transcribe`，不假定已安装）
- 用户的要求是翻译、润色、改写原文风格
- 输入是纯文字稿但不要求提炼知识点（直接读即可）

## 核心能力

此 Skill 只做一件事：**拿到直播转录文本 → 去噪 → 提取有价值知识点 → 输出结构化 MD。**

它不关心文本怎么来的，不涉及下载、转录、命名、git 同步——那些交给协作的 Skill 处理。

## 输入评估：5 秒扫描法

拿到直播文稿后，根据**文件大小 + 标题关键词**快速分档：

| 文件大小 | 典型内容 | 处理深度 |
|----------|----------|---------|
| **< 8 KB** | 开播测试、秒关、静默 | A 类：1-2 行说明，标记 `has_finance_content: false` |
| **8-40 KB** | 短答疑、部分闲聊夹杂金融 | B 类：中粒度，只摘 2-5 个核心知识点 |
| **40-80 KB** | 正常连麦/答疑/讲座 | C 类：深度总结，6-12 个知识点 |
| **> 80 KB** | 长场多人连麦/专题 | C 类++：可能需要分主题结构 |

**标题关键词预判**（以中文投资类直播为例）：

- **高概率有干货**：答疑、讲讲、市场、交易、期货、价值投资、预期、讲解、连麦答疑
- **中概率有干货**：山崩、谷底、猪周期、养殖、反转、底部、复盘、答疑
- **低概率有干货**：游戏名（MC、炉石、PVZ、原神）、打游戏、启动、等待、闲聊

### 输出产出物

| 级别 | 产出 | MD 大小 | 适用场景 |
|------|------|---------|---------|
| **A 类** | frontmatter + 1-2 行说明 | ~300-500 字节 | 纯游戏、极短场（<8KB） |
| **B 类** | frontmatter + 少量知识点 | ~1-3 KB | 游戏+闲聊混合场 |
| **C 类** | 完整结构化 MD | ~5-15 KB | 金融/交易主题场 |
| **C 类++** | 分主题 + 附洞察提炼 | ~10-15 KB | 长场（>80KB）多主题场 |

## 工作流

### 阶段 1：阅读与去噪

转录输出常为**字间空格格式**（如"我 今 天 讲 讲 市 场"），需先在理解层面剥离空格。

1. **扫描开头 10%**：判断基调（答疑/游戏/闲聊/混合）
2. **识别伪内容标记**：
   - 大量重复无意义词（"嗯 嗯 嗯""啊 啊 啊""哼"）→ 等待加载 / 思考过渡
   - 游戏音效描述 → 纯游戏，可跳过
   - 弹幕互动（"感谢xxx的舰长""家人们"）→ 社交填充，无留存价值
3. **锁定真实内容段**：当出现以下关键词时进入精读：
   - 逻辑论述类：因为、所以、本质、核心、我认为、我的看法
   - 交易框架类：预期差、赚钱效应、确定性、模式、纪律
   - 市场判断类：流动性、周期、泡沫、反转、趋势
   - 方法论类：买点、卖点、仓位、杠杆
   - 问答标记（连麦场景）：我、你、问、答

### 阶段 2：知识提取

从文本中提取**可沉淀为知识**的内容，剔除噪音。

**应提取的**：
- **框架性观点**：完整的论述链（前提→推理→结论→操作建议）
- **反直觉洞察**：与主流认知相悖且逻辑自洽的观点
- **量化数据**：具体数字、比例、价格区间、时间节点
- **案例与反例**：过往操作、成功/失败经验
- **情绪与信仰表达**：折射人格特质和投资哲学的言论

**应忽略的**：
- 游戏实况细节（打怪、出装备、附魔等）
- 个人生活闲聊（吃饭、睡觉、买房、过户等）
- 弹幕互动调味（感谢礼物、调侃观众）
- 重复/冗余论述（同一观点反复讲 5 遍以上，只取最佳阐述）
- 明显情绪化吐槽（戏剧性表达，除非揭示投资哲学）

### 阶段 3：结构化输出

#### Frontmatter（元数据层）

```yaml
---
source_video: BVID（如有）
source_title: 原标题（含日期）
upload_time: YYYY-MM-DD HH:MM:SS
duration_estimate: ~N 分钟/小时
generated_at: YYYY-MM-DD
has_finance_content: true/false
---
```

#### Body（正文层）—— 倒金字塔 + 主题归并

```
# 标题

## 核心立场（1-3 句话概括本场核心论点）

## 金融与交易知识点（按重要性排序）
### 1. 核心知识点标题
- 论点本身
- UP 主的论证过程
- 操作含义/推论
- ⚠️ 如果与之前观点矛盾，注明纠偏

> **📖 原文引用**
>
> （从原始转录稿中提取的对应片段，经 ASR 可读性优化）

---

### 2. 第二个知识点
...

## 自评/态度（保留人格色彩）
- UP 主情绪状态、自信程度、态度变化

> **📖 原文引用**
>
> （如有对应原文）

---

## 其他

## 其他
- 提到的其他标的清单
- 与之前观点的关联
- 值得跟踪的"未完成叙事"
```

#### 写作原则

1. **一个知识点 = 一个论证链**：不单写结论，写"为什么得出这个结论"
2. **优先记录首次出现的新观点**：重复观点简写或引用
3. **保留人格色彩**：口头禅、独特比喻、情绪爆发——这些才是辨识度
4. **不追求完美表述**：转录有错字正常，只提炼核心意思
5. **区分顺势观点与反共识观点**：反共识观点才是真正有价值的知识沉淀

### 阶段 4：原文引用注入

每个知识点在总结提炼之后，**必须附上对应的原文引用区块**，让读者能追溯观点来源、验证总结是否忠实于原文。

#### 引用格式

```markdown
> **📖 原文引用**
>
> （优化后的原文片段）

---
```

用 `---` 分隔线与下一个知识点隔开。

#### 引用选取规则

1. **精准对应**：引用片段必须与该知识点的论点直接相关，不堆砌大段无关原文
2. **完整论证链优先**：优先选取包含「前提→推理→结论」的完整段落，而非碎片化句子
3. **多段引用**：如果一个观点在原文中分多处阐述，可引用多段，用空行分隔
4. **人格色彩保留**：引用中保留 UP 主的口语化比喻、情绪表达，不改为书面语

#### ASR 转录文本优化规则

引用片段从 ASR 转录稿中提取时，需做以下可读性优化（**不改变原意**）：

| 优化类型 | 说明 | 示例 |
|---------|------|------|
| **修正同音词** | ASR 常见识别错误，按上下文修正 | `焦望` → `矫枉`、`能翻母猪` → `能繁母猪`、`比弗莫尔` → `利弗莫尔`、`波克希尔哈萨韦` → `伯克希尔哈撒韦` |
| **去除口语冗余** | 删除重复语气词、无意义复读 | `然后呢然后呢` → `然后`；`这个东西这个东西这个东西` → `这个东西` |
| **补全标点** | 按语义添加逗号、句号、问号、破折号等 | `他都是普通的人哎政策是人制定的` → `他都是普通的人，政策是人制定的` |
| **修正断句** | 将无标点的连续语句按语义分句 | 无标点长句 → 按语义断句分段 |

**禁止操作**：
- ❌ 添加原文中没有的内容或解释性文字
- ❌ 改变 UP 主的原意
- ❌ 将口语化表达改为书面语（如"挖肉""抬轿子""库库抄底"等保留原样）
- ❌ 删除有辨识度的人格化语言（口头禅、比喻、情绪表达）

#### 领域术语表（必查）

金融/交易领域的 ASR 同音词误转具有高频规律性，修正时**必须查表**：

- 术语表位置：`references/asr-finance-glossary.md`（本 Skill 目录下 references 文件夹）
- 表内含：字母/音节类（做T、股吧等）、专业术语类（能繁母猪、利弗莫尔等）、平台/产品名、以及「待观察区」（未人工确认条目**不得自动修正**）
- 表内每条均附「上下文判别提示」，仅在上下文支持时应用，不得机械替换
- 增量维护：首次需要回填时，将随包术语表复制到用户确认的知识库/输出目录，读取已有副本后增量维护；人工确认的新误转对写入该工作区副本，不修改安装目录。后续评审读取此副本（若无副本则只读随包表）。

> ⚠️ **注意**：此处的 ASR 优化是**内容层面**的修正（同音词、冗余、标点），
> 与 `asr-transcript-cleaner` 技能的**机械层面**清洗（去字间空格、规则化插标点）不同。
> 引用注入阶段需要 AI 理解上下文来做语义级修正，这是脚本无法替代的。

#### 适用范围

| 输出级别 | 引用要求 |
|---------|---------|
| **A 类** | 无需引用（内容本身极短） |
| **B 类** | 可选，建议为核心知识点添加 |
| **C 类及以上** | **必须**为每个知识点添加原文引用 |

### 阶段 5：分批写入（长文档防超时）

**为什么**：单份 C 类/C 类++ 总结文档可达 15-25 KB（知识点正文 + 原文引用），一次性写入极易触发 LLM 请求超时/中断，导致内容丢失与重复劳动。

**写入节奏**（按内容要点分批次输出）：

| 批次 | 内容 | 工具 |
|------|------|------|
| 第 1 批 | frontmatter + 标题 + 核心立场 | write |
| 第 2~N 批 | 每 3-5 个知识点为一批（含各自的 📖 原文引用区块） | edit（在已读取的唯一末尾锚点处追加） |
| 末批 | 自评/态度 + 其他（跨场关联、未完成叙事） | edit（在已读取的唯一末尾锚点处追加） |

**规则**：
1. 单批输出量控制在约 3-5 个知识点（含引用），不贪多
2. 先建骨架再填充：第 1 批可只含 frontmatter + 核心立场，后续批次先读取已写内容，再用 `edit` 的唯一末尾锚点按序追加；保留原锚点并附加新内容，不能用 `write` 覆盖已有批次
3. B 类（1-3 KB）文档可单批写完，无需分批
4. 分批不改变文档结构——最终成品与一次性写出的版本完全一致
5. 所有批次完成后再执行后续动作（文件落位、清理临时文件、git 提交）

## 常识陷阱与应对

### 陷阱 1：字间空格导致的假语义

```
原文：我 觉 得 市 场 已 经 到 了 顶 部
理解：我觉得市场已经到了顶部（正确）
误读：市场 经 到 了 顶（错误）
```

**应对**：按「词」而非「字」理解含义，尤其投资领域固定短语（预期差、赚钱效应、猪周期等）。

### 陷阱 2：口头禅被误判为知识点

常见非知识点口头禅："做 T 不是我的兄弟""成本不重要""XX一定到 N 元"。

**应对**：只有**首次出现且有完整论证链**的才记录为新知识点。后续重复简写。

### 陷阱 3：游戏/闲聊中的金融隐喻

主播偶尔用游戏隐喻市场（如"MC 里所有的猪都是能繁母猪"）。

**应对**：不作为体系化知识点，可作为「观察」附注。除非隐喻本身揭示了新的市场认知框架。

### 陷阱 4：噪音比例误判

60 分钟直播中真正有价值的金融内容可能只有 5-10 分钟。

**应对**：全文扫读 → 标记有价值段落 → 只精读这些段落。不为"不遗漏"去读整个游戏环节。

## 场景化处理策略

### 场景 A：开盘/盘中直播（盯盘场）

特征：实时看 K 线、情绪化喊单、数据零碎

**知识密度**：通常中等偏下。重点记录盘中特殊事件和主播的第一反应，而非长线观点。

### 场景 B：连麦答疑

特征：问答驱动，知识密度高

**知识密度**：最高。每个连麦可能产出一个独立知识点。按问题的**主题**而非时间顺序组织。

### 场景 C：专题讲座（"今天讲讲..."）

特征：系统性输出，完整的论证链

**知识密度**：最高。整篇 MD 应围绕**一个核心论点**展开，所有知识点都为核心论点服务。

### 场景 D：游戏娱乐场

特征：打游戏为主，金融内容偶发

**知识密度**：低。标记 `has_finance_content: false`，只摘少数金句，不做深度结构。

## 跨文档管理视角

当连续处理同一个主播的多场直播时，跟踪以下维度：

- **观点一致性**：是否推翻或修正了之前的观点？
- **认知进化**：对某个话题的理解是否随市场变化而深化？
- **消息验证**：之前的预判是否被后续事件验证？
- **持仓变化**：是否在某个时间点调整了核心持仓/方向？

在全量 MD 生成后，可进一步提炼**核心观点全景图**（将同一话题的所有论述合并为一条完整论证，标注时间线和认知演变）——这是更高阶的整合工作，不在单篇 MD 范围内，但应在单篇中为未来聚合打好基础（如使用一致的命名前缀）。

## 质量自检清单

输出前逐项检查：

- [ ] 是否遗漏了本场**首次出现的新观点**？
- [ ] 是否混入了**无论证链的噪音**作为知识点？
- [ ] frontmatter 字段是否完整？
- [ ] ⭐ 标记是否反映观点的真实重要度？
- [ ] 重复出现的观点是否写了**简写版本**而非再次长篇展开？
- [ ] 是否保留了主播的人格化语言，还是写成了"教科书"？
- [ ] 是否区分了「前瞻预判」和「事后归因」？
- [ ] C 类及以上输出：每个知识点是否附有 **📖 原文引用** 区块？
- [ ] 引用片段是否与知识点精准对应，而非堆砌大段无关原文？
- [ ] 引用中的 ASR 同音词是否已修正（如"焦望"→"矫枉"）？
- [ ] 引用是否保留了 UP 主的人格化表达，未改为书面语？
- [ ] C 类及以上输出：是否按「阶段 5」分批写入（3-5 个知识点/批），而非一次性输出全部内容？

## 忠实度评分标准（Review Gate）

> **本节的执行者是评审 subagent，不是主 agent。** 生成者用同一上下文自检无法发现编造与失真（自证陷阱）——这正是需要独立评审的原因。主 agent 的职责边界：注入本节标准 → 收评分报告 → 落盘分数 → 执行修订。**主 agent 不得自行打分。**

### 考核范围：仅忠实度一维

唯一问题：**总结中已写下的内容，是否忠实于源稿的实际内容。**

### 扣分类型（起评 100，按严重度扣减）

| 类型 | 定义 | 扣分 | 实测案例 |
|------|------|------|----------|
| 编造论证/因果链 | 总结中的论证在源稿中不存在 | -40 | 「风险已制度化分散」——源稿实为「不值得定价」 |
| 事实/方向错误 | 数字、方向、事件与源稿相反 | -40 | 「空黄金亏损」——源稿明确「赚的很多」 |
| 观点拼合错误 | 源稿两处独立表述被拼成一个论证 | -25 | 「资本也是散户」与「盈亏同源」原为独立表述 |
| 数据失真 | 量级/比例/时间节点偏离源稿 | -20 | 「两亿头」实为「一亿头」 |
| 误导性表述 | 表述有据但暗示了原文没有的关系 | -15 | 类比暗示「巴菲特重资产≈牧原同逻辑」 |
| 编者注混入 | AI 解释性内容未标注，写成 UP 主观点 | -10 | 预期差的教科书定义混入正文 |
| 引用臆改 | 引用区块过度书面化/加戏/偏离原意 | -10 | 口语「挖肉」被改为书面语 |

### 明确豁免（不得扣分——防误报）

- **漏收**：源稿有、总结没写——覆盖度不在本评审范围
- **结构/frontmatter 格式**：机械项，主 agent 的读回校验负责
- **噪音混入**：游戏/闲聊内容被收入——不构成不忠实
- **ASR 同音词未修正**：源稿本身错、总结照抄（如「木源」）不算；但**修错**（把玩梗当错字改掉）按引用臆改扣
- **重要度排序、简写程度、跨文档关联**：主观项

### 评分锚点与动作

| 分数 | 判定 | 主 agent 动作 |
|------|------|----------------|
| 90-100 | PASS | 落盘分数，完成 |
| 70-89 | 轻瑕疵 | 落盘分数；引用臆改/编者注类建议顺手修复并更新分数 |
| <70 | FAIL | 逐扣分点修订（edit）→ 复审 1 轮 |

### 评审报告输出格式

```
总分: N
扣分点:
1. [知识点X / 引用区块X / 核心立场] 类型 — 一句话描述（源稿依据：原文片段或段落位置）
2. ...
```

无扣分点时仅输出：`总分: 100 PASS`

## subagent 忠实度评审流程

### 触发与豁免

| 输出级别 | 评审 |
|---------|------|
| C 类 / C++ 类 | **必评**（写入文件后） |
| B 类 | 可选——建议对含具体数据、史实、操作细节的知识点评 |
| A 类 / 娱乐场轻维护 | 免评 |

### 调用规范（主 agent 执行）

1. 总结**已写入文件并验证**后，调用 `subagent({description: "评审总结忠实度", prompt: 完整评审任务})` 创建一个独立评审员。prompt 包含总结、源稿和术语表的绝对路径、下方任务及完整评分标准；明确只读评审、不修改文件，报告直接返回，不额外生成产物。后台结果按实际返回类型处理：若返回 jobId，用 `job_output` 收集；若返回可继续的 subagentId，等待完成通知，复审使用可用的新委派或续接方式。
2. 不使用未声明的 specialist 或团队工具；评审标准必须完整包含在独立评审员的 prompt 中，无需创建 Agent Teams。
3. prompt 模板（填入路径后原样注入，「忠实度评分标准」一节全文嵌入【评分标准】处）：

```
你是忠实度评审员。评审总结文件：
{总结文件绝对路径}
是否忠实于源稿：
{源稿文件绝对路径}

【评分标准】
{嵌入本 Skill「忠实度评分标准」一节全文：考核范围、扣分类型表、豁免清单、评分锚点、报告输出格式}

【任务】
逐个知识点、逐段引用，在源稿中定位对应依据；无法定位的按扣分类型表定性扣分。
不考核漏收/结构/噪音——只考核已写内容是否忠实于源稿。

【domain 术语纠正】
评审过程中发现的 ASR 同音词/术语误转（如"不替"→做T、"股巴/古巴"→股吧），按术语表处理：
1. 先读术语表 {术语表绝对路径}（主 agent 提供：优先用户工作区维护副本，否则随包只读表），仅当上下文支持且表内已人工确认时才在报告中列为修正建议
2. 待观察区（未人工确认）条目只作提示，不要求修正
3. 在报告末尾追加一节「术语纠正建议」：列出 [位置] 误转→正确 + 上下文依据，供主 agent 落实修订并回填用户工作区的术语表副本（人工确认后，不写安装目录）

【输出格式】
总分: N
扣分点:
1. [位置] 类型 — 一句话描述（源稿依据）
无扣分点则输出: 总分: 100 PASS
```

### 报告处理与落盘（主 agent 职责）

1. **落盘**：frontmatter 追加两个 B 模板体系字段：

   ```yaml
   review_score: 92          # 忠实度评分（subagent 评审，复审后为终评分）
   reviewed_at: 2026-08-31   # 评审完成日期
   ```

2. **FAIL（<70）**：把每个扣分点转为修订动作——回读源稿定位真实表述后用 edit 精确修复；修订完成后发起**复审 1 轮**
3. **复审 prompt**：向原评审员续接时补充上轮扣分点与修订说明；若新建评审员，必须重新提供总结、源稿、术语表绝对路径、完整评分标准和扣分点清单。要求逐项核查并重新给总分；复审后更新 review_score，**无论结果如何不再进入下一轮**（防循环）
4. 报告中的扣分点清单不落盘——修订完成后即消解；若复审仍 FAIL，可将剩余扣分点以 `<!-- review-pending: 描述 -->` 注释留在文件中待人工复核（可选）

### 降级路径

环境无 `subagent` 类工具时，主 agent 改用**强化自检**替代：逐个知识点在源稿中**写出证据段位置**（而非凭记忆打勾），无法定位的必须回读源稿复核或删除该表述。此路径效果弱于独立评审，仅作 fallback。)
