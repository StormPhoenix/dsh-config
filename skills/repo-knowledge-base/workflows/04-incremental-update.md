# Workflow 04 · commit 增量分析与文档更新

本文档指导 LLM 在收到一笔（或多笔）新 commit 时，判断是否需要更新知识库，并执行相应的更新动作。

## 自主执行原则（最高优先级）

> 与 SKILL.md 「核心行为原则」一致，本 workflow 要求 LLM **自主完成全流程**，不要中间停下来问用户。

**收到 commit 通知到完成汇报之间，只有以下 2 种情形可以中间停顿问用户**：

1. 判定起争议（例如同一 commit 可以合理地归为 🟡 或 🔴，不同走向产出不同文档动作）
2. 需要用户补充**仓库外**信息（如本次变更背后的产品决策）

**以下都不是停顿理由**：
- “这次有 7 笔 commit，要不要逐笔处理？”→ 不问，直接逐笔评级后统一更新
- “diffStat 被截断，请你提供完整 diff”→ 不问，自己跑 `git show <hash>`
- “我计划更新 5 篇 tech 文档 + overview + changelog，要继续吗？”→ 不问，直接干
- “For your reference…”后跟一串列表让用户选 → 不要这样做

**反例 vs 正例**：

| 场景 | ❌ 反例 | ✅ 正例 |
|---|---|---|
| 收到 7 笔 commit | “这是 7 笔，计划这样处理... 要继续吗？” | 逐笔评级 → 直接更新全部文档 → 汇报结果 |
| diffStat 被截断 | “信息不全，请你补齐” | 调用 `git show <hash> --stat` 自己拿完整清单 |
| 明显 🔴 需要动 5 篇 tech | “我计划动 5 篇 tech 文档，你让我动吗？” | 直接动 → 完成后明示"本次触发了知识库 X 篇文档更新" |

## 落盘验证义务

所有声称完成的文档变更都必须满足：

1. **真实调用过写入工具**（`edit` / `write`）——不能只输出叙述文字
2. **工具调用正常完成且没有错误** ——检查当前工具的实际返回值；`edit` / `write` 不要求 `success` 字段，发生异常或错误时不得声称完成
3. **完成后自检**（推荐）：
   - `bash` 查询 <kb_root> 文件时间戳 看文件时间戳是否为本次会话时间
   - 必要时 `read` 读改后片段确认内容落到位
   - 使用 `read` 的 offset/limit 读取 changelog 末尾，确认添上本次记录

如果上一个回合的 LLM 是你，且你计划只汇报不写入——请重读本节，这是严重违反。

## 核心方法 · 三色影响等级

每笔 commit 必须打上一个色标，决定后续动作。**不评估等级就不动文档**。

### 🟢 低影响（Low）

**典型特征**：
- commit type 为 `style:` / `chore:` / `test:` / `docs:`（仅文档）/ `build:`（仅打包配置）/ `i18n:`
- 仅修改 README、注释、版本号
- 仅新增或微调测试用例
- 纯样式调整（CSS、组件圆角、间距）
- 重命名变量、提取常量等等价重构（不动接口签名）

**动作**：
- ✅ 在 `changelog/YYYY-MM.md` 追加一行
- ❌ 不修改 overview，不修改 tech 文档

**示例 commit**：
- `style: 统一按钮圆角` 🟢
- `test: 补充 plugin 边界用例` 🟢
- `chore: 升级 lockfile` 🟢
- `docs: 修正 README 拼写` 🟢

### 🟡 中影响（Medium）

**典型特征**：
- commit type 为 `feat:` 但仅在已有模块内增加小功能（不新增模块、不动公开接口）
- commit type 为 `fix:` 修复非接口层的逻辑问题
- commit type 为 `refactor:` 但仅在模块内部拆分文件，不动外部调用方式
- 已有配置项的扩展（新增可选字段，不破坏旧配置）
- 添加新的子工具/子能力到已有体系（如 plugin 系统里加新内置 plugin）

**动作**：
- ✅ 修改相关 tech 文档对应章节（通常是"核心抽象"或"优点总结"小幅扩充）
- ✅ changelog 追加，并在条目里注明改了哪个 tech 文档
- ❌ 一般不改 overview（除非改动涉及新增的子能力恰好该列入索引）

**示例 commit**：
- `feat: 增加插件 prompt budget 配置` 🟡 → 更新 plugin-system 的 budget 章节
- `refactor: 调整插件工具策略保存入口` 🟡 → 更新 plugin-system 的"保存链路"小节
- `fix: 同步插件工具策略保存状态` 🟡 → 仅 changelog；除非 tech 文档已涵盖状态机

### 🔴 高影响（High）

**典型特征**：
- 新增整个模块 / 删除模块 / 模块大面积迁移
- 修改公开接口（含 IPC 协议、protocol/types、外部 API 签名）
- 改变核心抽象（数据结构关键字段、状态机变化）
- 新增重要的设计决策（多层防御新增一层、新增双存储、新增并发隔离机制）
- 大规模重构（commit 标题里有 "继续拆分" "整体重构" "迁移到"）
- 涉及安全 / 权限 / 沙箱机制

**动作**：
- ✅ 必须修改至少一篇 tech 文档（可能新增 tech 文档）
- ✅ 必要时更新 overview（模块清单、tech 索引、技术栈）
- ✅ changelog 追加，并明示影响等级与文档变更清单
- ✅ 在 commit 总结里**显式提示用户**："本次更新涉及 X，已同步知识库"

**示例 commit**：
- `feat: 迁移 LLM Wiki 为资源内置插件` 🔴 → 改变模块归属，更新 overview + 相关 tech
- `refactor: 继续拆分 main 进程职责` 🔴 → 主进程模块图变化，更新 electron-main tech
- `feat: 支持 zip 宠物包导入` 🔴 → 新增完整功能闭环，可能新增 tech 文档

## 判断流程

```
┌─────────────────────────────────────────┐
│  收到 commit 信息（hash + 标题 + diff）  │
└──────────────────┬──────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│ Step 1：看标题 type 与关键词，初判色标   │
└──────────────────┬──────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│ Step 2：看 diffStat 文件清单，对照监控信号│
└──────────────────┬──────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│ Step 3：拿不准 → 看完整 diff（深读）     │
└──────────────────┬──────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│ Step 4：执行对应等级动作                 │
└─────────────────────────────────────────┘
```

## Step 1 · 标题快速初判

按照 conventional commits 规范的 type，给一个**初始猜测**：

| type | 初始等级 | 何时上调 |
|---|---|---|
| `style:` | 🟢 | 涉及大范围 UI 重构时 → 🟡 |
| `chore:` / `build:` / `ci:` | 🟢 | 改打包目标 / 发布机制 → 🟡 |
| `test:` | 🟢 | 极少上调 |
| `docs:` | 🟢 | 改的是仓库内官方架构文档 → 🟡 |
| `fix:` | 🟡 | 修接口层 / 安全机制 → 🔴 |
| `refactor:` | 🟡 | "继续拆分" / 改抽象 → 🔴 |
| `feat:` | 🟡 | 新模块 / 新接口 / 新协议字段 → 🔴 |
| 无 type 或 `BREAKING:` | 🔴 | 默认按 🔴 处理 |

## Step 2 · 用 diffStat 对照监控信号

读取 commit 的 `diffStat`（文件改动清单），对照各 tech 文档"监控信号"章节列出的关键路径：

- **命中关键路径** → 至少 🟡，必须读对应 tech 文档检查
- **命中"接口稳定性"标记的文件** → 直接 🔴
- **命中关键词**（commit 标题包含某个 tech 文档列出的关键词）→ 至少 🟡

## Step 3 · 何时主动深读 diff

不要每个 commit 都拉全 diff，按需深读：

### ✅ 必须深读的情况

- 已经确定 🔴 → 必须读 diff 才能写出准确的文档更新
- 标题与 diffStat 信号矛盾（如 `style:` 但改了 protocol/types.ts）
- diffStat 显示新建文件 ≥ 2 个 / 删除文件 ≥ 2 个
- 改动行数 > 500 行
- 接口/类型文件被改动

### ⚠️ 选择性深读

- `feat:` 但改动 < 100 行 —— 看 diffStat 推断即可
- `fix:` 标题清楚说明问题域，且 diffStat 在已知模块内

### ❌ 不需要深读

- 🟢 的 commit
- 仅改 README / changelog / .gitignore / lockfile

### 工具调用

```
bash({description: "检查 Git 记录", command: "git show <hash> --stat", workdir: "<repo_root>"})            # 看完整 diffStat
bash({description: "检查 Git 记录", command: "git show <hash>", workdir: "<repo_root>"})                    # 看完整 diff
bash({description: "检查 Git 记录", command: "git log <hash> -1 --format=%B", workdir: "<repo_root>"})      # 看完整 commit message
```

## Step 4 · 执行更新动作

按等级执行：

### 🟢 动作（仅 changelog）

```
先 read 该月 changelog，再使用 edit({file_path, old_string, new_string}) 精确插入
  追加一行：- {hash} 🟢 {一句话描述}
```

### 🟡 动作（tech 文档 + changelog）

```
1. 找到要改的 tech 文档（命中监控信号的那篇）
2. 定位到对应章节（通常是"核心抽象"或"优点总结"）
3. 用 edit 做精确插入或修改（不要重写整篇）
4. changelog 追加，注明改了哪个文档的哪节
```

### 🔴 动作（多篇文档 + 显式提示用户）

```
1. 列出受影响的所有 tech 文档 / overview 章节
2. 必要时新建 tech 文档（按 03-tech-analysis.md 规范）
3. 必要时改 overview 的模块清单（第 3 章）或 tech 索引（第 7 章）
4. changelog 追加详细条目，标 🔴
5. 在汇报给用户的 commit 总结里**显式标明文档变更**
```

## 多 commit 一起来怎么处理

后台任务一次拉到 N 个 commit 时（如 commitCount: 5）：

1. **每个 commit 单独评级**，不要笼统打一个标签
2. **看是否构成同一主线**：标题相邻、改动相关 → 在 changelog 里合并描述
3. **取所有 commit 的最高等级**作为本次同步的总等级
4. **文档更新只做一次**：哪怕 5 笔都改了 plugin 系统，只在 plugin-system.md 上做一次综合更新

## 常见判错纠偏

- **把 `feat:` 全打 🟡**：错。新增模块或公开接口要 🔴。
- **把样式 commit 全打 🟢**：错。如果是设计系统级改动（如统一控件样式覆盖整个设置页），可能 🟡。
- **把多 commit 笼统打一个等级**：错。逐个评，最后取最高。
- **🔴 但忘了显式告知用户**：错。🔴 必须在汇报里明示文档变更，否则使用者不会注意到。

## 完成后回到何处

- 🟢 → 直接结束本次处理
- 🟡 → 检查改完的 tech 文档是否符合 `03-tech-analysis.md` 的四段式（防止小修破坏结构）
- 🔴 → 如果新增了 tech 文档，回到 `02-overview-writing.md` 更新 overview 索引
