# Workflow 03 · tech/ 框架设计分析单篇规范

本文档指导 LLM 给单个模块编写一篇 tech 设计分析。tech 文档是知识库的"价值核心"——它回答"这块代码为什么这么设计、好在哪、要监控什么"。

## 选题原则

不是每个模块都需要 tech 文档。优先给以下模块写：

### ✅ 强烈建议写

- **核心抽象层**（协议、内核、Context、Session 等运行时基础）
- **有非平凡设计决策的模块**（如多层防御、双存储、并发隔离）
- **架构亮点**（commit 历史中作者反复打磨的、官方文档专门写过的）
- **边界模块**（IPC、权限、安全边界）

### ⚠️ 选择性写

- 业务功能模块（仅当其本身代表一个完整功能闭环时）
- 大型 UI 模块（仅当组件设计本身有结构性亮点）

### ❌ 不要写

- 工具函数 / 类型定义 / utils
- 简单的 CRUD 模块
- 自动生成的代码
- 第三方库的薄封装

**总数控制**：中大型仓库通常 tech 文档 **6 - 12 篇** 即可，超过 15 篇说明粒度太细。

## 标准结构 · 四段式

每篇 tech 文档**严格遵循**以下四段结构：

### 1. 设计动机（Why）

回答"为什么需要这个模块？没有它会怎样？"

- **业务/技术背景**：1-2 段，描述这个模块解决的问题
- **现有方案的不足**（如适用）：为什么不用更简单的方案
- **核心设计目标**：3-5 条，每条一句话

⚠️ **不要直接说"为了实现 X 功能"**，要说出**真正的设计驱动力**（如"为了让 LLM 调用与 harness 的边界不被业务代码污染"）。

### 2. 核心抽象（What）

回答"这个模块由哪些关键概念/数据结构/类组成？"

- **关键数据结构 / 类 / 接口**：每个用一段说明，附源码路径
- **职责边界**：每个抽象只负责什么、不负责什么
- **它们的关系图**（可选）：用 ASCII 图或简单列表表达

代码引用规范：
```markdown
关键文件：`packages/agent/src/plugin/types.ts:42`

核心接口：
```ts
interface Plugin {
  name: string
  hooks: PluginHooks
  // ...
}
```
```

### 3. 优点总结（Value）

回答"这种设计相比朴素方案好在哪？"

⚠️ **本节是 tech 文档的核心价值**——必须给出**具体、可验证**的优点，不要写空洞的"模块化、可扩展"。

好的优点总结举例：
- ✅ "fail-closed pre-hook 让权限校验失败默认拒绝执行，避免错误状态下放行"
- ✅ "harness 强制路径规范化，杜绝 LLM 用相对路径逃逸到 workspace 外"
- ✅ "subagent 只读隔离让并发安全和缓存命中两个目标同时达成"

避免的写法：
- ❌ "代码结构清晰" / "易于维护" / "高度模块化" —— 太空洞
- ❌ "符合 SOLID 原则" —— 是结论不是分析
- ❌ "支持插件扩展" —— 只是事实陈述，没说为什么这样设计就好

每条优点用 1 段话展开，2-5 条为宜。

### 4. 监控信号（Watch）

回答"后续 commit 改了什么文件 / 关键词，应该重新审视这篇 tech 文档？"

这是**专为后续增量分析使用**的指引。列出：

- **关键路径**：哪些目录/文件的改动会影响本模块设计
- **关键词**：commit 标题中哪些词应触发深读
- **接口稳定性**：哪些接口算公开 API（变化即 🔴）

示例：
```markdown
## 监控信号

**关键路径**：
- `packages/agent/src/plugin/`
- `packages/agent/src/plugin/types.ts`（接口定义，变化即 🔴）

**关键词**：plugin / hook / strategy / budget / activation

**视为接口的文件**：
- `types.ts`：接口签名变化必须更新本文档
- `builtins.ts`：内置插件清单变化需更新模块清单
```

## 长度控制

- 单篇 tech 文档 **150 - 400 行** 为宜
- 短于 100 行 → 大概率是写薄了，回去补"动机"和"优点"
- 超过 500 行 → 考虑拆分（比如 `plugin-system.md` + `plugin-budget.md`）

## 写作风格要求

1. **客观描述设计，不评价作者**
   - ✅ "这种分层让 X 与 Y 解耦"
   - ❌ "作者的设计非常优秀"

2. **明示推测**
   - 当从代码反推设计意图时，必须写 "推测设计动机是..."
   - 不要把推测包装成事实

3. **少用形容词，多用机制**
   - ✅ "通过 catch + 日志静默吞掉异常，保证主流程不受影响"
   - ❌ "异常处理非常健壮"

4. **代码引用宁多勿少**
   - 关键设计点必须附文件路径（最好带行号）
   - 接口、关键函数签名建议直接贴代码片段

## 编写步骤

1. **快速读关键文件**：模块入口 + 核心类型/接口 + 1-2 个典型实现 + 测试目录命名
2. **回查 commit 历史**：搜索该模块最近 30 个 commit，看作者反复改了什么
3. **对照官方文档**：如果仓库已有该模块的 docs/，先读它再补充
4. **按四段式起草**：先写动机，再核心抽象，再优点总结，最后监控信号
5. **回头检查优点总结**：每条优点是不是具体可验证？空洞的删掉重写
6. **加路径与代码引用**：所有"关键文件""核心接口"都要带绝对/相对路径

read({file_path: "<模块>/<core-implementation>.ts"})
通过 bash 列出目录 <模块>/test/（将目标路径转为绝对路径；不使用 shell 读取文件正文）

# 看 commit 历史

bash({description: "检查 Git 记录", command: "git log --grep=<关键词> --oneline | head -20", workdir: "<repo_root>"})

# 看测试看出意图
read({file_path: "<模块>/test/<core>.test.ts"})
```

## 常见陷阱

- **陷阱 1：把"是什么"写成全文，没写"为什么"**
  → 强制留够一节给"设计动机"，且不少于 1/4 篇幅
- **陷阱 2：罗列所有文件而不是关键抽象**
  → 模块里 15 个文件不代表你要写 15 段，挑核心 3-5 个
- **陷阱 3：把使用文档当成设计分析**
  → tech 文档的读者是想理解"为什么这么设计的"工程师，不是要学怎么用的用户
- **陷阱 4：监控信号写得太宽泛**
  → "改了 plugin 目录就更新本文档" 这类规则没用，应当具体到子路径或关键词
