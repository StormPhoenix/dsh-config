## 2. 三色影响等级（核心判定规则）

每笔 commit 必须打色标，色标决定动作。

### 🟢 低影响

- type 为 style / chore / test / docs / build / i18n
- 仅样式 / 注释 / 测试 / 配置微调
- **动作**：仅 changelog 追加一行

### 🟡 中影响

- 已有模块内的小 feat / fix / refactor
- 已有配置项扩展、子能力新增
- **动作**：修改对应 tech 文档相关章节 + changelog

### 🔴 高影响

- 新模块 / 删模块 / 模块迁移
- 修改公开接口 / 协议字段 / 关键数据结构
- 安全或权限机制变化
- **动作**：修改/新建 tech 文档 + 必要时更新 overview + changelog + 显式告知用户

> 详细规则见 Skill 中的 `workflows/04-incremental-update.md`。

## 3. 增量更新流程

收到新 commit 时按以下步骤执行：

1. **看标题** —— 用 conventional commits type 初判等级
2. **看 diffStat** —— 对照各 tech 文档的"监控信号"章节
3. **拿不准 → 看完整 diff**（`git show <hash>`）
4. **执行对应等级动作**
5. **🔴 时显式告知用户文档变更**

## 5. 何时主动深读 diff

不要每个 commit 都拉全 diff，按需深读：

- ✅ **必须深读**：🔴 commit / 接口文件改动 / diffStat 与标题矛盾 / > 500 行 / 新建文件 ≥ 2
- ⚠️ **选择性深读**：feat 但 < 100 行 / fix 已知模块内
- ❌ **不需要深读**：🟢 commit / 仅改 README / lockfile / .gitignore

## 6. 文档写作风格

### 共通规则

- **客观**：描述设计，不评价作者
- **明示推测**：从代码反推意图时写"推测"
- **少形容词，多机制**：说"通过 catch + 日志吞掉异常"，不要说"非常健壮"
- **代码引用宁多勿少**：关键设计点必带路径

### overview 风格

- 入口性，结构稳定
- 三列模块索引表是核心
- 不写设计深度（深度留给 tech）
- 总长度 300-600 行

### tech 风格

- 严格四段式：动机 / 抽象 / 优点 / 监控
- 单篇 150-400 行
- 优点必须具体可验证

### changelog 风格

- 一笔 commit 一行为主
- 🟡/🔴 必须写文档更新动作
- 月度有 ≥ 10 笔时补主线总结
